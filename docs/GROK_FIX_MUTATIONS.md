# Mutation correctness fixes

Scope: findings 6, 7, 8, 10, 11 and 12 from `build/grok-review-5b3a058.md`, reconciled against the existing modernization changes. All validation uses disposable databases/projects; no live user program is modified.

| Finding | Applied behavior | Regression evidence |
| --- | --- | --- |
| 6: ambiguous target programs | `bulk_transfer_labels`, `bulk_region_transfer`, `create_functions_at_addresses`, and `string_anchor_matcher` resolve exact name, project path, URL or `program_id` through shared `ProgramSelection`/`ProgramIdentity`. Both source and destination are resolved before mutation. Duplicate display names return tool errors. Each explicitly selected database has a scoped consumer lease for actual execution, released on every return/failure path. | Two same-name ProgramDB objects: ambiguous selectors fail; exact ID creates a function only in the intended database. A native target releases its GUI consumer when the write transaction begins: the tool keeps it alive through the write, then releases it afterward. |
| 7: variable retype acknowledged without writing | Both `set_local_variable_type` and `variables(action=retype)` share `VariableRetypeSupport`. Database locals/parameters use `Variable.setDataType`; decompiler-only symbols use `HighFunctionDBUtil.updateDBVariable` in a transaction. Failed resolution/decompilation/write returns `isError=true`. | Retype a real database local through both public tools and inspect its type. A native decompiler fixture exercises inferred symbol persistence. Invalid type preserves original. |
| 8: selective clear removes unselected code | Preview captures exact selected code units/functions, deduplicates overlaps, and apply clears that plan. Half-open boundaries that bisect selected units fail before writing. Unselected instructions/data and function definitions remain. | All four instruction/data flag combinations, preview preservation, partial-unit rejection and overlapping ranges on a mixed instruction/data/function fixture. |
| 10: failed native creation leaves partial writes | Function creation, candidate apply and region transfer use one transaction per call and roll back the entire call after failure/cancellation. Region verification mismatches also roll back any speculative function creation. Reports reset committed counts and separately count rolled-back labels/functions; prior success rows identify rollback. Existing caller transactions are rejected rather than treating nested transactions as savepoints. | A successful creation followed by invalid memory rolls back both function and disassembly. A valid candidate followed by a non-executable target does likewise while preserving pre-existing instructions. Region tests cover later native creation failure, later verification mismatch, and successful verified transfer. |
| 11: implicit type replacement / parser mutation | Creation defaults to `conflict_policy=fail`; replacement requires explicit `replace`. The rule applies to structures, enums, typedefs and their dependencies. C parsing uses isolated staging and lookup managers before resolving into the program. Typedef creation honors its category. | Incompatible structure/enum/typedef collisions preserve existing types. Native C parsing conflicts and invalid syntax preserve existing fields; explicit replacement changes the intended type. |
| 12: rejected image base still imports successfully | Base-address failures roll back and propagate before `LoadResults.save` or UI opening. Import failure responses are tool errors. | Invalid/out-of-range bases preserve original base; real raw-loader import with invalid base creates no saved domain file; valid base changes correctly. |

Compatibility: existing tool names and existing result fields remain. Intentional corrections are fail-closed ambiguous selectors, truthful variable persistence, selective clear semantics, whole-call rollback, and explicit type replacement. These mutations change the in-memory Ghidra database; saving remains a separate operation except for successful imports.
