Start with runtime_capabilities(include_programs=false), then page list_binaries to select programs. Copy the exact program_id into related calls; source_program and target_program also accept these opaque IDs. Names and project paths can collide. Never split, truncate or reconstruct an ID, and never assume GUI focus remains unchanged. Resolve ambiguity before proceeding.

Check GUI/headless mode, enabled tools, services, language, revision, changeability and save capability. Diagnostics do not probe external BSim servers or repository health. Offline saved database inspection does not describe unsaved state in a running Ghidra program.

Prefer bounded queries and batches. Follow continuation fields; restart paging if the inventory/program revision changes. Inspect per-row errors, short reads and truncation. Truncated output is not complete evidence. Use the complete JSON text fallback if the client does not expose structuredContent; recover spilled results through the client's supported file-reading workflow.

Generic task_id values belong to this server's in-memory manager. Fast reads may finish inline. Follow task submissions with wait_task(include_result=true) for bounded waiting and an optional complete result; use get_task_status when the payload exceeds that response budget. RESULT_EXPIRED and RESULT_TOO_LARGE describe payload retention, not mutation failure. A timeout ends the wait, not the operation. Cancellation requests do not prove execution stopped. Generic records do not survive JVM restart: inspect program state before retrying a mutation. These tools are not MCP Tasks extension handles. BSim has a separate durable job journal and bsim_* controls; never pass its job_id to wait_task.

For cross-program matching, verify language/context compatibility and inspect evidence, ambiguity and scan completeness. Use native VT or an explicitly supported matcher mode. A heuristic score or capped hit list does not prove uniqueness. Missing function definitions are prerequisites to investigate, not permission to create every candidate automatically.

Before transfer, inspect existing names, signatures and provenance. Use dry_run for whole-operation validation. preview_annotations controls optional annotations; it is not a whole-operation dry run. Preserve analyst work unless replacement is explicitly requested. Reuse supplied preview tokens only while program state and operations remain current. Inspect committed, preserved, failed and rolled-back outcomes; a task ID or successful rename does not prove complete transfer success.

VT match review, applied annotations and saves are distinct. Use port_ledger(get) at an exact source function entry to obtain its current_fingerprint. Include explicit port_metadata in each bulk_transfer_labels row: operation_id, exact source_program_id, source_address, source_fingerprint and method. The transfer records a bounded applied_unverified NOTE/PORT checkpoint in the annotation transaction. One checkpoint per destination replaces previous history; repeat operations do not append history. Use port_ledger(list/get) to resume, then verify with operation_id and expected_target_revision; the server rechecks the stored source and target fingerprints. Verification checks bytes and annotations, not semantic equivalence. Save the target separately to persist the checkpoint. Unsaved source identities cannot provide cross-session recovery.

If post-mutation verification fails, distinguish an applied edit from unavailable or stale verification. Never automatically repeat the edit solely to recover its result. Process-local modification numbers are not persistent fingerprints.

Save deliberately: save_program persists program edits; VT session saves and save_project_session have different scopes. Inspect each result. Repository operations may require save, checkout/check-in or GUI merge resolution. A readonly changed program is not a durable checkpoint. Do not claim persistence from annotation success, a copied extension archive or listener shutdown.
